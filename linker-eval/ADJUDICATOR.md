# פוסק ה-LLM (שלב 3)

שני חלקים: (0) הוכחה שהגישה ישימה — **תקרת אורקל**, ו-(1) הרצות POC אמיתיות של Haiku.

## שלב 3.0 — תקרת אורקל (הצעד החשוב ביותר) — [oracle_ceiling.py](oracle_ceiling.py)

הפוסק המתוכנן רק **בוחר** מבין מועמדי ה-matcher; הוא לא מחפש בטקסט גולמי. לכן התקרה שלו =
האם התשובה הנכונה בכלל **בחלון המועמדים** (שורות הבסיס תחת אותו `daf_key`). כל שורת זהב
מפורקת ל: `hit` (ה-argmax כבר צדק) · `recoverable` (הזהב בחלון אך ה-argmax טעה — **ההזדמנות
של הפוסק**) · `unreachable` (הזהב מחוץ לחלון — בעיה במעלה הזרם, LLM לא יעזור).

**58 אחרונים מיושרים, 27,354 שורות:**

| | ערך |
|---|---|
| matcher נוכחי | 49.5% |
| **תקרת אורקל** | **95.4%** |
| מרחב שיפור (recoverable) | **+45.9 נק'** |
| unreachable (במעלה הזרם) | 4.6% בלבד |
| מ-recoverable עם מרווח-ציון < 30 | 92% |

**המסקנה שמאמתת את כל שלב 3:** ב-95% מהמקרים התשובה כבר בחלון — צוואר הבקבוק הוא **הבחירה**,
לא החלון. ורק 4.6% אבודים במעלה הזרם. 92% מהשורות הניתנות לשחזור הן מרווח-ציון נמוך, כך
שסיגנל triage זול (מרווח בין המועמד המוביל לשני) יתפוס כמעט את כולן.

## שלב 3.1 — POC אמיתי של Haiku — [adjudicate.py](adjudicate.py)

לכל דף: Haiku מקבל את קטעי הגמרא הממוספרים + רצף קטעי הפירוש, ומחזיר לכל קטע את מספר קטע
הגמרא (או 0). מדידה על אותן שורות, מול אותו זהב. Backend: ה-CLI `claude -p --model haiku`
(בלי צורך במפתח API; להחליף ל-Batch API בהמשך).

**פני יהושע על בבא קמא, 5 דפים ראשונים (27 שורות, תקרת אורקל 88.9%):**

| תצורה | hit@set | מול matcher |
|---|---|---|
| matcher (בסיס) | 63.0% (17/27) | — |
| Haiku — בלי הקשר, כל השורות מוכרעות | 70.4% (19/27) | +7.4 |
| Haiku — הקשר-שכנים + triage + "אשר-או-תקן" | 63.0% (17/27) | +0.0 |

**מסקנה כנה: על המדגם הזה Haiku (דרך ה-CLI) לא מנצח את ה-matcher באופן נמדד.** שתי התצורות
חובקות את ה-63% של ה-matcher — ההפרש ביניהן הוא **רעש** (27 שורות, Haiku לא-דטרמיניסטי).
האורקל מוכיח שיש 89% להשיג, אבל Haiku-ב-CLI עדיין לא מממש אותו.

ממצא ביניים שכן התגלה בבירור: מדיניות "שלח כל שורה מסומנת והחלף עיוור את בחירת ה-matcher"
**פוגעת** — Haiku שובר שורות שה-matcher צדק בהן (בעיית ה-false-alarm של הדגל: 79% מסומנות,
רובן נכונות). "אשר-או-תקן" (להראות ל-Haiku את הניחוש הנוכחי ולשנות רק בביטחון) עצר את הנזק
אבל לא הוסיף lift.

## שלב 3.2 — Sonnet + מועמדים רחבים = פריצת הדרך

שני תיקונים מ-3.1: מודל חזק (Sonnet) והרחבת קטעי הגמרא ל-340 תווים (החשוד: הדיבור-המתחיל
נפל מעבר ל-180). מצב "הכרע-הכול + אשר-או-תקן".

**פני יהושע על בבא קמא, 10 דפים ראשונים (38 שורות), מצב "הכרע-הכול + אשר-או-תקן":**

| תצורה | hit@set | מול matcher | % מהתקרה |
|---|---|---|---|
| matcher (בסיס) | 63.2% (24/38) | — | 71% |
| Haiku 3.1 (מועמדים קטומים 180) | ~63% | +0 (רעש) | — |
| **Haiku — מועמדים רחבים (340)** | **81.6% (31/38)** | **+18.4** | 91% |
| **Sonnet — מועמדים רחבים** | **86.8% (33/38)** | **+23.7** | 97% |
| תקרת אורקל | 89.5% (34/38) | — | 100% |

**שתי מסקנות מכריעות:**
1. הכשל של Haiku ב-3.1 היה **קטימת המועמדים, לא המודל** — הדיבור-המתחיל נפל מעבר ל-180
   תווים. עם חלון רחב, Haiku הזול קפץ מפריטי ל-**+18.4 נק'** (91% מהתקרה).
2. Sonnet רק **5 נק' מעל Haiku-רחב**, וההבדל מרוכז בדף אחד (ג': Haiku 4, Sonnet 6); בכל שאר
   הדפים הם זהים. כלומר המודל הזול לוכד כמעט את כל השיפור.

## הצעד הבא: העלות כמעט נפתרה — נותר לייצב ולהרחיב

1. **Haiku-רחב הוא סוס העבודה** — זול ולוכד 91% מהתקרה. אפשר escalation ל-Sonnet רק על
   השארית הקשה (פער 5 נק') אם צריך.
2. **Batch API + JSON schema** במקום ה-CLI (~2-4 דק'/דף, לא-דטרמיניסטי, timeouts שדרשו
   fallback ל-matcher) — חובה למדידה על מאות דפים ולפרודקשן; 50% הנחה.
3. **מדידה גדולה ומגוונת** — 38 שורות נותנות איתות ברור, אבל צריך ≥300 שורות וספרים נוספים
   (מהרש"א, הפלאה — עתירי super ו-multi) למספר בר-פרודקשן.
4. **כיול חלון המועמדים** — 340 עבד; לבדוק אם מלא/רחב יותר סוגר גם את פער דף ג'.
